## 1. 수학 독립 검증

이 스펙은 "Staged Missions: N/A"(기존 에피소드 UI 개선)이므로 미션 대신 Section 6의 검증 문제 V1~V3을 직접 풀었다. 근거로 쓴 코드: `episodes/01-calculus-howitzer/index.html`(#ang: min 10, max 80, step 0.5), `src/model/constants.ts`(G=9.8, CHARGES=[60,75,93,115]), `src/model/ballistics.ts`(`muzzlePos`: 지면+6 m에서 포신 12 m), `engine/src/ui/components.css`, `episodes/01-calculus-howitzer/src/style.css`.

### V1 손잡이 중심 x 좌표
- 독립 풀이: 손잡이 폭 w는 트랙 양 끝에서 손잡이가 완전히 들어가도록 예약된다. 즉 값이 최소일 때 중심은 왼쪽 끝에서 w/2, 최대일 때 L−w/2이고, 그 사이는 값에 대해 선형이다.
  f(θ) = (θ−10)/(80−10) = (θ−10)/70
  **x(θ) = w/2 + (θ−10)/70 · (L−w)**  [px]
  확인: θ=10 → w/2, θ=45 → w/2 + 0.5(L−w) = L/2, θ=80 → L−w/2.
  L=210, w=16이면 x(30)=8+(20/70)·194=63.4, x(45)=105, x(80)=202.
- 스펙 답과 비교: **일치** — answers.md: `x(θ) = w/2 + (θ − 10)/70 · (L − w)`. 확인점(θ=10 → w/2, θ=80 → L − w/2, θ=45 → L/2)도 1차 풀이와 같다. 다만 answers.md는 "트랙 왼쪽 끝 기준"이라고만 적어 그 왼쪽 끝이 border box인지 margin box인지 밝히지 않아 아래 모호함이 남는다. 1차 풀이의 L, w, x 예시(210, 16, x(80)=202)는 아래 V2 정정에 따라 206, 16, 198로 읽어야 한다.
- 지적: [사소함] L을 "무엇의 폭"으로 정의했는지 명시해야 한다. 입력 요소의 border box 폭과 실제 트랙(엔진별 inset·UA 기본 margin 포함) 폭은 몇 px 다를 수 있고, 위 식은 후자에만 성립한다. 답안에 "L = 손잡이가 움직이는 트랙 폭(입력 요소 실측)"이라고 못박는 편이 2차 비교와 구현 검증에 모두 안전하다.
- (2차) 1차 지적의 방향은 맞았고, 실제 차이는 **4 px**로 확인됐다. `getBoundingClientRect().width`는 border box 폭이므로 360px에서 이 값은 210이 아니라 **206 px**이다(근거는 V2). θ=80의 손잡이 중심은 border box 왼쪽에서 L − w/2 = 198 px, θ=10은 8 px이다. range 입력의 UA `margin:2px`(Chromium `html.css`, Firefox `forms.css`, WebKit `html.css` 모두 동일)는 border box 바깥이라 식에 들어가지 않고 x의 원점만 2 px 민다. "L = 입력 요소 border box 폭, x = 그 box의 왼쪽 끝 기준"으로 못박아야 한다.

### V2 360px 화면의 숫자 간격·겹침
- 독립 풀이: 360px에서 슬라이더 실폭은 CSS로 계산된다.
  `.wrap` padding-inline 16×2 → 328, `.panel` border 1×2 + padding 14×2 → 298, `.row`의 ± 버튼 36×2 + gap 8×2 = 88 → **L = 210 px** (스펙 값과 일치).
  숫자 8개(10,20,…,80)는 7칸을 균등 분할하므로 간격 = (L−w)/7 = 194/7 = **27.714 ≈ 27.7 px**.
  라벨 폭 22 px 기준 남는 틈 = 27.7 − 22 = **5.7 px > 0 → 겹치지 않는다**(간격의 약 21%). 5° 눈금 간격은 194/14 = 13.9 px이므로 작은 눈금끼리도 겹치지 않는다.
  양 끝: "10"의 중심은 트랙 왼쪽 끝에서 8 px, "80"은 202 px이므로 22 px 라벨은 트랙 밖으로 각각 3 px씩 나간다. 다만 `.panel` padding 14 px·`.row` gap 8 px 안쪽이므로 잘리지 않는다(컨테이너에 overflow 클립이 없을 때).
- 스펙 답과 비교: **결론 일치, 중간값은 1차 풀이가 틀렸다** — answers.md도 `(210 − 16) / 7 ≈ 27.7 px`, 여유 5.7 px로 1차와 같은 수를 낸다. 결론(간격 > 라벨 폭, 겹치지 않음)은 맞지만 **둘 다 같은 실수**를 했다. 210 px은 `.row`가 입력 요소에 배정한 flex 슬롯이고, range 입력의 UA `margin:2px`가 border box 바깥에 붙으므로 실제 border box는 **206 px**이다(Chromium `html.css`, Firefox `forms.css`, WebKit `html.css` 모두 `input[type="range"]{margin:2px}`). 정정하면 이동 거리 190 px, 숫자 간격 (206−16)/7 = 190/7 = **27.1 px**, 여유 5.1 px, 5° 눈금 간격 13.6 px이며, 45°는 40°·50°에서 각각 13.6 px 떨어진다(answers.md V2 "주의"의 13.9 px도 13.6으로 정정). 1차 풀이의 x 좌표를 border box 왼쪽 기준으로 다시 쓰면 θ=80 → 198(1차 202), θ=45 → 103(1차 105), θ=40 → 89.4(1차 91.1)이다. 끝 라벨의 3 px 외곽 결론은 그대로다(UA margin 2 px이 여유를 오히려 늘린다).
- 지적(2차): [권장] L은 flex 슬롯 210이 아니라 border box **206 px**이다. 오버레이 원점을 border box 왼쪽에 맞추고 식에 210을 쓰면 θ=10에서 0, θ=45에서 +2, θ=80에서 **+4 px**가 되어 NFR-002(≤2 CSS px, 10°·45°·80°에서 측정)를 80°에서 넘는다. 원점을 flex 슬롯(=margin box) 왼쪽에 맞추면 반대로 θ=10에서 −2, θ=45에서 0, θ=80에서 +2 px로 끝에서 딱 허용치를 다 쓴다. "L = `#ang.getBoundingClientRect().width`(360px에서 206), 원점 = 그 box의 왼쪽 끝"으로 고치면 오차가 0이 된다. 숫자 간격도 27.1 px(여유 5.1 px)로 적어야 한다. 스펙 §4·§Assumptions·answers.md V2 세 곳이 같은 수정 대상이다.
- 지적(1차, 유지): 없음 — 겹침 여부·양 끝 잘림 결론은 위 수치 정정 후에도 뒤집히지 않는다. (끝 라벨의 3 px 외곽은 4절 구현 조건으로만 언급)

### V3 발사 높이가 있을 때 최대 사거리 각
- 독립 풀이: 착탄 지면을 y=0, 발사점을 (0, h)로 두면
  R(θ) = (v cosθ / g)·( v sinθ + √(v²sin²θ + 2gh) )   [Wikipedia "Maximum distance of projectile"의 y₀ 식]
  dR/dθ = 0을 풀면 **tanθ\* = v / √(v² + 2gh)**, 즉
  **θ\* = arctan( v / √(v² + 2gh) )**.
  h=0이면 45°로 되돌아온다(h>0이면 45°보다 작아진다).
  v=75, h=14.5, g=9.8: v²+2gh = 5625+284.2 = 5909.2, √ = 76.87, tanθ\* = 0.97566 → **θ\* = 44.294° ≈ 44.3°**.
  수치 확인: R(45°)=588.13 m, R(44.3°)=588.30 m (차 0.17 m, 0.03%). 40°=582.0, 42°=586.5, 47°=585.8 m.
  → **45°보다 작다.** (h가 클수록 더 작아진다.)
  참고로 이 게임의 실제 조건(포구 높이 6+12sinθ, 굴곡 지형, 잔여 화면 폭 1000 m)에서 각도만 0.25° 간격으로 훑어 최대를 찾으면, 2호(75 m/s)는 seed 60개에서 44.5~47.0°(평균 45.8°), 1호(60 m/s)는 41.5~50.0°였다. 목표 지면이 포구보다 높으면 최적각이 45°를 넘는다.
- 스펙 답과 비교: **일치** — answers.md: `θ* = arctan(v/√(v²+2gh))`, v=75·g=9.8·h=14.5 → 44.3°, "h>0이면 45°보다 작다". 유도(착탄이 h 낮은 진공 포물선의 수평거리 최대화)와 결론이 1차 풀이와 같다. 1차 풀이의 수치도 재확인했다: R(44.294°)=588.301 m, R(45°)=588.131 m(차 0.170 m). 1차 풀이가 틀린 곳은 없다.
  - 2차 추가 확인(적대적): h를 상수 14.5가 아니라 각도에 따라 변하는 h(θ)=6+12sinθ로 두어도 최적각은 **44.51°**로, 44.3°와 0.2° 안에서 같다(해석해를 상수 h에 적용한 근사의 정당성 확인). 평지·진공·h=0이면 수치 재현도 45.0°로 돌아온다.
- 지적: [권장] 이 결과는 Section 4의 라벨 "진공·평지 최대"와 정면으로 맞물린다. 진공·평지라도 **발사점과 착탄점의 높이가 같다는 조건**이 있어야 45°가 최대이고, 이 게임은 포구가 지면+14.5 m라서 진공·평지에서도 최대는 44.3°다. 라벨·주석 문구에 그 조건을 넣거나("45°: 지면 발사 기준 최대", "45° 근처 최대(진공·평지)"), 최소한 answers.md와 notes 문구에 조건을 명시해야 C-004(조건 없는 "최대" 금지)의 취지를 실제로 지킨다. 게임 화면에서 0.17 m 차이는 관측되지 않으므로 구현이 틀린 물리를 가르치지는 않지만, 스펙이 스스로 44.3°를 계산해 놓고 라벨은 45°를 최대로 단정하는 불일치는 남는다.
- (2차) 이 지적은 **answers.md가 같은 방향을 지지한다**. answers.md V3 "의미"는 "45° 주석은 '진공·평지(발사점과 착탄점이 같은 높이)'라는 조건을 밝혀야 한다 (C-004)"고 정확히 적었다. 문제는 spec.md 쪽이다: §4 라벨 "진공·평지 최대" / "max range (vacuum, flat)", FR-003, User Story 2, SC-003 어디에도 높이 조건이 없다. 주석은 구현에서 그대로 화면 문구가 되므로 answers.md의 결론을 spec.md 라벨에 반영해야 한다. 지적 등급은 [권장]을 유지한다(0.17 m 차이는 화면에서 관측되지 않아 틀린 물리를 가르치지는 않음).
- (2차) [권장] V3 문제 문장 "h ≈ 14.5 m(**자주포 2호 장약**, 포구 높이)"는 포구 높이가 장약에 딸린 값처럼 읽힌다. 실제로는 `muzzlePos`의 기하(지면+6 m, 포신 12 m, sinθ)에서 나오고 장약과 무관하다. 식은 h를 독립 변수로 두므로 답에는 영향이 없지만, "포구 높이 h ≈ 14.5 m(45°일 때, 게임 기하)"로 고쳐야 PRJ-001의 [game value] 구분과도 맞는다.

## 3. 교육 설계

목표 1(10° 단위로 위치 읽기) → 목표 2(45° 찾기 + 조건 인식)의 순서 자체는 쌓인다. 목표 1이 없으면 45°를 "찾는" 행위도 성립하지 않으므로 우선순위 P1/P2 배치도 맞다. 미션이 N/A인 것은 기존 에피소드 개선이라 헌장 PRJ-006상 허용된다.

- [권장] 45° 주석이 **튜토리얼 1장부터** 보인다. 현재 튜토리얼은 4장에서 "45°가 사거리 그래프의 꼭대기"를 발견하게 구성돼 있는데(그래프 위 점·접선·퀴즈), 슬라이더 라벨이 그 결론("최대")을 처음부터 제시하면 4장의 발견 학습이 약해진다. ① 4장 완료 전에는 굵은 눈금만 보이고 주석은 숨기기, ② 처음부터 보이되 "왜 그런지는 4장에서" 같은 한 줄을 붙이기, ③ 그대로 두기 — 중 하나를 **의도적으로 선택해 스펙/plan에 적어야** 한다. 지금은 이 선택이 스펙에 없다.
- [사소함] "진공·평지 최대"는 "무엇의 최대"인지가 문구에 없다. 1장 학습자는 아직 "사거리"라는 말을 배우지 않았다. 짧게 유지해야 하므로 주석 줄을 "45° = 진공·평지 사거리 최대"처럼 한 줄 노트로 두는 편이 안전하다(4절 배치 문제와 같은 해법).
- [권장] SC-003("45° 표시 어디에도 조건 없는 '최대' 문구가 없다")을 앱 전체로 읽으면 C-001(튜토리얼 문구 불변)과 충돌한다. 4장 본문 "① 그래서 45°가 가장 멀리 가요", 4장 퀴즈 선택지 "45°가 이 장약의 최대 사거리라"에는 조건이 붙어 있지 않다. SC-003을 "새로 추가하는 눈금·주석에 한해"로 범위를 명시해야 달성 가능한 기준이 된다.
- [권장] (2차) **학습 목표 2를 재는 성공 기준이 없다.** SC-001은 목표 1(30°·45°·60° ±2.5° 맞추기)만 재고, "조건을 함께 인식한다"(목표 2)에 대응하는 SC가 없다. SC-003은 문구 검사일 뿐 학습자가 조건을 읽었는지는 재지 않는다. SC를 하나 더 두거나("45° 주석의 조건 문구를 학습자가 지적할 수 있다" 같은 관찰 기준), 목표 2를 "45° 위치를 찾는다"로 줄이고 조건 인식은 학습 목표에서 빼는 편이 정직하다. 지금은 목표 2의 절반이 검증 밖이다.
- [권장] (2차) **45라는 숫자가 눈금 어디에도 없다.** §4는 "10°·20°·…·80°에 숫자. 45°는 굵은 눈금과 짧은 주석 '진공·평지 최대'"로 정하고, answers.md V2도 "45°는 숫자 대신 굵은 눈금과 아래 주석으로 표시"라고 확인한다. 45는 40과 50 사이의 5° 눈금 하나이므로 찾을 수는 있지만, 학습 목표 2의 "**바로** 찾고"와 SC-001(45°를 ±2.5° 안에 3번 중 3번)을 굵은 눈금의 위치만으로 만족해야 한다. 주석에 숫자를 넣어 "45° · 진공·평지 최대"(영어 "45° · max range (vacuum, flat)")로 두면 45°를 세지 않고도 읽을 수 있고, 1차의 "무엇의 최대인지 모호함"까지 한 줄에서 같이 풀린다. 이 문구는 약 100 px이므로 숫자 줄이 아니라 **별도 줄**에 두는 배치(4절 첫 항목)를 전제로 한다.
- [사소함] (2차) FR-006("30°·60° 대칭 단정 금지")은 대응하는 Acceptance Scenario도 SC도 없다. Assumptions에서 "슬라이더에는 표시하지 않는다"고 이미 정했으므로 FR-006은 기능 요구가 아니라 **금지 조건**이다. Constraints로 옮기거나 "새 눈금·주석에 대칭 표시를 넣지 않는다"는 테스트 문장으로 바꿔야 요구사항 표가 실제 검증 항목과 맞는다.
- [사소함] (2차) SC-004("착탄 결과, 튜토리얼 진행은 변경 전과 같다")는 이 미션이 `e2e/parity.spec.ts`의 스크린샷 비교를 의도적으로 깨뜨리는 것과 긴장 관계다. C-005를 "스크린샷만 제외"로 좁히면 SC-004는 계속 지켜지지만, 스펙에 그 연결이 적혀 있지 않아 구현자가 SC-004를 이유로 눈금을 넣지 못하는 것으로 오해할 수 있다. SC-004에 "(픽셀 비교 예외는 C-005)" 한 줄을 붙이면 충분하다.

## 4. 구현 가능성

- [권장] 45° 주석의 배치가 검증 범위 밖이다. 360px에서 숫자 간격은 27.1 px인데 "진공·평지 최대"는 9 px 글자 8자로 약 72 px다. 45°(x=103)에 중심을 맞춰 **숫자와 같은 줄**에 두면 이웃 숫자 40°(x=89.4)·50°(x=116.6)와 중심 간격이 13.6 px뿐이라 반드시 겹친다(22 px 숫자 라벨끼리도 5.1 px 여유로 붙어 있다). 영어 "max range (vacuum, flat)"는 약 110 px로 더 심하다. 주석을 별도 줄(눈금 → 숫자 → 주석 3단)로 두거나 눈금 아래 짧은 리더선을 쓰는 식으로 **세로 배치를 스펙에 정하고**, NFR-001·SC-002의 "겹치지 않음"에 숫자 8개뿐 아니라 45° 주석도 포함해야 한다.
- [권장] 눈금 오버레이의 **기준 상자**를 스펙이 정하지 않았다. `.row`는 flex이고 `#ang`에는 UA `margin:2px`가 붙으므로, ① `.row`를 기준으로 absolute 배치하면 2 px 밀리고, ② `#ang`을 감싸는 새 wrapper를 두면 flex 슬롯 210 px와 border box 206 px가 섞인다. "`#ang`의 border box에 정확히 겹치는 wrapper(`position:relative`, 폭 100%)를 두고 그 안에서 x(θ)를 계산"처럼 **기준 요소를 한 문장으로 못박아야** NFR-002(≤2 px)가 검증 가능해진다. 위 V2의 206 px 수정과 같은 원인이다.
- [권장] NFR-002(≤2 CSS px)의 **검증 수단이 없다**. 네이티브 range의 손잡이는 DOM 요소가 아니라 `getBoundingClientRect()`로 위치를 얻을 수 없고, 엔진별 기본 손잡이 폭·트랙 inset도 다르다. 16 px를 하드코딩하면 실제 폭이 20 px일 때 오차는 양 끝에서 (16−20)/2 = 2 px(중앙 0)로 허용치와 정확히 같아진다. plan에서 ① `appearance:none`으로 손잡이 폭을 CSS로 고정하거나, ② 스크린샷 픽셀 비교로 실측하거나, ③ 손잡이 폭을 런타임에 재는 방법 중 하나를 정해야 한다. (①은 조작감이 바뀌지 않는지 NFR-003과 함께 확인 필요)
- [권장] NFR-004("Chromium·Firefox·WebKit에서 모두 보임")는 현재 CI로 검증할 수 없다. `playwright.config.ts`에 projects가 없고 `channel: 'chrome'` 단일 구성이라 Chromium만 돈다. Firefox/WebKit project를 추가하거나, NFR-004를 "Chromium 자동 + Safari/Firefox 수동 확인"으로 낮추고 확인 절차를 plan에 적어야 한다.
- [권장] C-005(이전 비교 테스트)의 범위를 구체화할 수 있다. `e2e/parity.spec.ts`에서 실제로 깨지는 것은 `screenshots match legacy` 2건(fullPage 픽셀 비교)뿐이고, `snapshot()`이 비교하는 DOM·문구와 `field`/`chart` 캔버스 dataURL은 눈금과 무관하다. 즉 **스크린샷 테스트만 패널 영역 마스크/제외하고 나머지 비교는 그대로 유지**하면 계산·튜토리얼 불변(C-001, SC-004) 가드를 잃지 않는다. C-005를 "비교 테스트 전체 완화"로 해석하지 않도록 plan에 이렇게 적는 편이 좋다.
- [권장] References 2행의 인용이 부정확하다. `Range_of_a_projectile`(→ Projectile motion) 문서에는 "Maximum range (높이 y₀)"라는 절이 없다. 문서가 주는 것은 y₀를 넣은 d(θ) 식이고, θ\*는 그 식을 미분해 얻어야 한다. "같은 문서의 y₀ 사거리 식 + 미분 유도(answers.md)"로 고치거나, θ\* 공식을 실제로 싣고 있는 출처로 바꿔야 한다. (행이 `needs verification`인 것은 적절)
- [사소함] 눈금 위치를 **CSS 백분율로 두는지 JS px 계산으로 두는지**가 스펙에 없다. Edge Case가 "창 크기를 바꾸거나 회전해도 어긋나지 않는다"를 요구하므로, 각 눈금을 `left: calc(var(--thumb)/2 + <f>*(100% - var(--thumb)))`(`<f>` = (θ−10)/70, 미리 계산한 수) 같은 백분율 식으로 두면 리사이즈 대응이 공짜다. 반대로 로드 시점에 px로 계산해 넣으면 resize 리스너나 `ResizeObserver`가 필요하고, 없으면 768↔1280 전환에서 어긋난다. plan에 한 줄로 정해 두면 테스트(리사이즈 후 재측정)도 명확해진다.
- [사소함] 다크 모드·테마 토큰(NFR-005)은 기존 `--line`/`--muted`/`--accent`를 쓰면 충족된다. 다만 눈금 오버레이는 장식이므로 `aria-hidden="true"`를 주고, 슬라이더 자체의 값 노출(`#angV`, aria-valuetext)은 그대로 두는 편이 좋다. 지금 요구사항에는 이 처리가 없다.
- [사소함] Edge case "튜토리얼이 슬라이더를 강조(어두운 막)할 때"는 현재 발생하지 않는다. 튜토리얼 target은 `field`·`eq`·`chart`뿐이고 조작 패널을 강조하는 단계가 없다. 방어적으로 남겨도 해는 없지만, 검증 항목으로 계획에 넣으면 확인할 대상이 없으므로 "해당 없음"으로 정리하는 편이 낫다.
