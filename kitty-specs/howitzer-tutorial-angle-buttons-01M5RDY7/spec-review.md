## 1. 수학 독립 검증

§5 Staged Missions가 N/A(기존 에피소드 UI 개선)이므로 미션 대신 §6의 검증 문제 V1을 직접 풀었다. 이 미션은 탄도·지형·조준 계산을 바꾸지 않으므로(C-001) 수학 검증 대상은 360px 레이아웃 기하 하나이고, 여기에 상태 규칙이 기존 코드의 데이터 흐름과 맞는지 부수 확인을 더했다. `research.md`는 없고 `research/` 폴더도 비어 있었다.

근거 코드: `engine/src/tutorial/tutorial.css`(카드 폭·padding·border·overflow), `engine/src/ui/theme.css`(전역 box-sizing), `engine/src/tutorial/index.ts`(카드를 document.body에 붙임, render/emit), `episodes/01-calculus-howitzer/src/missions.ts`(15단계 본문·게이트·land 기록), `episodes/01-calculus-howitzer/src/game.ts`(land, shot.ang, updateStats), `episodes/01-calculus-howitzer/src/main.ts`(input 리스너), `index.html`(슬라이더 10~80, step 0.5).

계산 도구는 쓰지 않았다 *(1차 기준 — 2차에서 `python3`로 아래 px·대비 값을 전부 재계산해 확인했다. 결과는 요약과 각 절의 "2차" 표시 참고)*. 아래 px 값은 CSS 값의 정확한 산술이고, 글자 폭만 폰트 메트릭 근사(±2px)임을 표시한다. 대비는 WCAG 상대휘도식(선형화 후 L = 0.2126R + 0.7152G + 0.0722B, 대비 = (L밝은+0.05)/(L어두운+0.05))으로 손계산했고 소수 셋째 자리에서 반올림했다.

### M1 360px 카드 내용 폭과 44px 버튼 5개 (V1)
- 독립 풀이:
  - 카드는 `position:fixed`로 `document.body`에 붙으므로 `width:min(560px, calc(100% - 24px))`의 `100%`는 뷰포트 폭이다(패널·`.wrap` 폭이 아니다). 360px에서 카드 border box = min(560, 360 − 24) = **336px**.
  - 전역 `box-sizing:border-box`이므로 내용 폭 = 336 − 좌우 padding 16×2 − 좌우 border 1×2 = **302px**. `border-top:4px`은 폭에 영향이 없다.
  - 카드가 세로로 넘치면(`max-height:48vh; overflow:auto`; 15단계는 문단·표 때문에 넘친다) 클래식 스크롤바 15px이 레이아웃 뷰포트를 줄여 내용 폭이 **287px**가 된다. 휴대폰의 오버레이 스크롤바는 폭을 먹지 않으므로 302px다.
  - 5×44 = 220px. 302px에서는 82px(간격당 20.5px), 287px에서도 67px(간격당 16.75px)가 남는다. 현재 `.tut-body .act`는 padding 8px 12px, border 1px, 15px/1.55라 높이가 8+8+23.25+2 = **41.25px**로 44px에 2.75px 모자란다. '30°'의 폭은 대략 22px(글자) + 24px(padding) + 2px(border) = **약 48px**(폰트 메트릭 근사)이므로 5×48 = 240px, 4×8px 간격이면 272px로 287px 안에 들어간다.
  - 결론: **한 줄에 들어간다.** 폭은 문제가 아니고, 높이를 44px 이상으로 올리는 것이 필수다.
- 스펙 답과 비교: **일치** — answers가 302px·한 줄 가능으로 적은 결론이 1차와 같다. 2차에서 `python3`로 재계산해 확인한 값: 카드 border box 336, 내용 폭 302(오버레이 스크롤바)·287(클래식 15px), 5×44 = 220, 현재 버튼 높이 8+8+23.25+2 = 41.25(15px × 1.55 = 23.25). answers의 유도식(`min(560, 360−24)`, `−2·16 −2·1`)도 1차와 같다.
  - 다만 answers의 마지막 줄("기존 버튼 '30°' 폭 ≈ 52px, 5·52+4·4 = 276 ≤ 302 → 한 줄")은 302px에서만 성립한다. 1차가 지적한 클래식 스크롤바 287px 경우에는 5·52 + 4·4 = 276 ≤ 287로 아직 들어가지만 여유가 11px뿐이고, R9에서 요구한 8px 간격을 넣으면 5·52 + 4·8 = 292 > 287로 **넘친다**. 즉 answers의 "여유가 있다"는 문장은 간격을 4px로 유지할 때만 참이다. 답 자체(302px)는 맞다.
- 지적: [사소함] S1 — V1의 '내용 폭'은 스크롤바 환경에 따라 302px(오버레이) 또는 287px(클래식 15px)다. 답을 하나로 못박으면 Playwright Chromium의 360px 뷰포트(클래식 스크롤바)에서 302를 기대했다가 실패할 수 있다. '카드 border box − padding − border, 실제 측정은 `#tut`의 사각형에서'라고 정의하고 두 값을 함께 적는 편이 안전하다. '들어가는가'의 답은 두 경우 모두 예라서 결론은 바뀌지 않는다. → **2차: 유지.** answers도 302만 적어 S1이 그대로 유효하다. 그리고 위에 적은 대로 287px에서는 8px 간격이 안 들어가므로 S1은 사소함이 아니라 R9와 묶어 다뤄야 한다.

### 부수 확인 — 상태 규칙과 기존 코드의 정합
- 독립 확인:
  - '표에 기록된 발사만'(DM-2) ↔ `on.land`의 `if (!r.out && r.v0 === 75) s.exp.push(...)`. 화면 밖(`out`)과 다른 장약은 제외된다. 일치.
  - '착탄해 기록되는 순간' ↔ `S.shot.ang`은 발사 시점에 고정되고 `land()`가 그 값을 Result로 넘긴다. 비행 중 슬라이더를 바꿔도 기록 각도는 발사 각도다. 일치.
  - '서로 다른 각도 4개' ↔ 게이트 `new Set(s.exp.map(q => q.ang)).size >= 4`. 버튼 각도가 아닌 37.5°도 1개로 세므로 Edge Case와 일치.
  - SC-001('각도 버튼만 써서 정확히 4발'): 2호(75 m/s)·평지·진공 근사에서 R = v²sin2θ/g는 30°/60° 497m, 40°/50° 565m, 45° 574m이고 포구 x ≈ 70m를 더해도 567~644m로 화면(착탄 판정 x ≤ 1040m) 안이다. 지형이 낮은 각의 포탄을 일찍 가로채도 '기록'은 되므로 4발로 게이트가 열린다. 성립.
  - 슬라이더 값은 10 + 0.5k라 모두 이진 정확값이고, 버튼 각도(30/40/45/50/60)와 `===` 비교가 안전하다. 문자열('30.0' vs '30')로 비교하면 깨지므로 숫자 비교여야 한다.
  - 단계를 나갔다 들어오면 `go()`가 `st = {}`로 새 상태를 만들므로 기록이 초기화된다. 일치.
  - 같은 각도를 슬라이더로 다시 쏘면 표의 `by[각도]`가 덮어써지고 집합 크기는 그대로다. 막지 않는다는 DM-1과 일치.
- 지적: [사소함] S2 — §4는 '장약이 2호로 고정되고'라고 단정하지만 코드의 `enter`는 `setCharge(75)`로 맞출 뿐 잠그지 않는다. 장약 버튼은 계속 눌리고, 다른 장약 발사는 `r.v0 === 75` 필터로 조용히 기록에서 빠진다. 관측 동작(2호만 기록)은 Key Entity와 맞으므로 기능 오류는 아니지만, 문구를 '2호로 맞춰 두고 2호 발사만 기록한다'로 고치거나 실제로 잠가야 학습자가 왜 표에 안 들어오는지 헷갈리지 않는다. → **2차: 유지·확인.** `missions.ts:227` `enter:()=>{...setCharge(75)}`에 잠금이 없고, `#charges` 버튼은 `main.ts:54`에서 `setCharge`로 계속 동작한다. `vel`은 hidden input이지만 사용자가 장약 버튼으로 바꿀 수 있다. 문구("locked")와 코드가 실제로 어긋난다. R10에서 말한 것처럼 15단계에서 장약을 바꾸면 그 발사가 표에 조용히 빠지므로, 이 미션의 "남은 각도만 고르면 된다" 목표와도 충돌한다.

NFR-002에 합격 조합을 하나 명시하는 편이 낫다: `--ink` 채움 + `--bg` 글자(13.31:1, 기존 `.mode`의 선택 상태와 같은 패턴) 또는 accent를 더 어둡게 조정. 이렇게 하면 "색 외 단서"도 채움으로 자동 충족된다.
- R2: [권장] '쏜 각도'를 "회색"이라고만 적어, 구현이 글자색만 `--muted`로 바꾸는 가장 작은 변경을 택할 수 있다. 그 경우 밝은 테마에서 '보통'(파랑, 4.82:1)과 '쏜 각도'(회색, 4.83:1)의 상대휘도가 사실상 같아(0.1305 vs 0.1300) 흑백·저시력에서 구분되지 않고, US3-3·NFR-002·SC-003을 스스로 위반한다. §4 상태 표의 '보이는 모습'에 상태별 단서를 못박아야 한다. 예: 보통 = 투명 배경 + 파랑 테두리, 현재 = ink 채움, 쏜 각도 = `--line` 회색 채움 + muted 글자 + (선택) "쐈음" 표식. 채움 대비는 회색 1.34:1로 약하지만 색이 아닌 면적 단서라 흑백에서도 보인다. 최소한 "글자색만 바꾸는 구현은 안 된다"는 문장이 필요하다.
- S3: [사소함] §4가 "장약이 2호로 고정"이라 쓰지만 75 m/s가 게임용 값이라는 표기([game value])가 스펙 어디에도 없다. 기존 값이라 새로 검증할 필요는 없으나, PRJ-001은 수식·물리값 옆에 출처·성격을 적게 하므로 §7이나 §4에 한 줄로 남기는 편이 일관된다.
- S4: [사소함] References 1행이 WCAG 2.5.5를 인용하며 44×44을 근거로 쓰는데, 이 기준은 **AAA**이고 AA에는 2.5.8(24×24)이 있다. 헌장 PRJ-004가 44를 요구하므로 요구 자체는 정당하지만, 표에 "Level AAA"를 적어 두어야 독자가 AA 준수 근거로 오해하지 않는다. → **2차: 유지·확인.** URL 본문 제목이 "Target Size (Enhanced) (Level AAA)"이고 "at least 44 by 44 CSS pixels" 문장도 확인했다. 1차 서술이 맞다.
- R11: [권장] **NFR-002의 '비활성 글자 3:1'은 저장소의 기존 비활성 스타일과 충돌한다.** `tutorial.css:24`(`.tut-ctrl button:disabled{opacity:.45}`), `:29`(`.tut-nav button:disabled{opacity:.55}`)가 `opacity`로 흐리게 한다. '쏜 각도' 버튼을 같은 방식으로 처리하면 밝은 테마에서 muted 글자가 **1.89:1**, 어두운 테마에서 **2.33:1**로 NFR-002의 3:1에 미달한다(opacity 0.45 기준. 3:1을 넘기려면 두 테마 모두 opacity ≥ 0.72가 필요하다). 게다가 `opacity`는 글자·테두리·채움을 한꺼번에 흐리게 해 "채움으로 상태 구분"이라는 R2의 단서까지 약화시킨다. 계획에서 비활성 상태를 `opacity`가 아니라 **색 토큰 지정**(예: 배경 `--line`, 글자 `--muted` — 이 조합은 3.62:1/4.49:1로 통과)으로 만들라고 명시해야 한다. 이 미션은 "완전 비활성"이 요구라 `disabled` 속성은 그대로 쓰되, 시각 처리는 opacity가 아니어야 한다.

## 3. 교육 설계

목표(실험한 각도와 남은 각도 구분) → US1(쏜 각도 비활성, P1) → US2(현재 강조, P2) → US3(휴대폰·보조 기술, P3)의 순서는 쌓인다. P1이 없으면 "남은 각도만 고르기"가 성립하지 않으므로 우선순위도 맞고, 선수 지식 "없음"도 15단계(4장 첫 실험)의 위치와 맞다. 미션이 N/A인 것은 기존 에피소드 개선이라 PRJ-006상 허용된다. 설명 없이 건너뛰는 개념은 없다. 다만 두 가지가 걸린다.

- R3: [권장] 4발 게이트를 채우는 조합에 60°가 반드시 들어가지 않는데, 15단계 본문은 4발을 채운 직후 "30°와 60°도 서로 비슷하죠?"라고 단정한다(`missions.ts:235-236`). 학습자가 30·40·45·50으로 끝내면 60°를 한 번도 쏘지 않았는데 화면이 60°를 봤다고 말한다. 기존 게이트의 한계이지만, 이 미션의 목표가 "실험을 빨리 끝내기"라 60°를 건너뛸 확률이 오히려 높아진다. 4장의 핵심 관찰(30↔60 대칭)을 놓치므로 다음 단계의 "같은 거리를 맞히는 각도가 두 개" 설명도 근거를 잃는다. 선택지: ① 게이트를 "서로 다른 4개 + 30°와 60° 포함"으로, ② 문구를 실제 기록에 맞춰 조건부로(기록에 30·60이 있을 때만 그 문장), ③ 그대로 두고 SC에 "60° 미실험 허용"을 명시. 지금 스펙은 "단계·진행 조건·문구는 바뀌지 않는다"(§5)라 ②③ 중 하나를 의도적으로 골라 적어야 한다.
  - **2차 보강 — 이 미션이 위험을 실제로 키운다.** `walkTutorial`은 `.act`를 순환하며 누르므로 테스트에서는 30→40→45→50 순서로 채워져 60°가 빠진다(실제 자동 진행도 같다). 각도 버튼이 비활성이 되면 남은 버튼이 줄어 순환 주기가 짧아지므로, "4발 중 60° 포함"이 더욱 보장되지 않는다. 또 SC-001은 "정확히 4발"만 재고 **어느 각도인지**는 재지 않으므로 이 결함을 통과시킨다. SC-001에 "4발의 각도가 서로 다르다"는 이미 게이트가 보장하니, 추가로 "15단계 문구가 30·60을 단정하지 않도록 ②를 택한다"를 성공 기준 옆에 적는 편이 좋다. 참고로 진공 근사에서 2호(75 m/s)의 각도별 사거리는 30°=497m, 40°=565m, 45°=574m, 50°=565m, 60°=497m이고 포구 x≈70m를 더해도 화면(착탄 x ≤ 1040m) 안이므로, **어떤 4조합을 골라도 4발이 모두 기록된다**(게이트 도달성은 문제 없음).
- S5: [사소함] 학습 목표가 "실험을 빠르게 끝낸다"는 UI 효율 목표로만 읽힌다. §2의 수학 개념(발사각과 사거리의 관계)과 연결하려면 "각도를 바꿔 가며 사거리 변화를 관찰하는 데 집중하게 한다"처럼 한 구절을 붙이는 편이 목표·개념·SC가 한 줄로 이어진다.

## 4. 구현 가능성

전체적으로 범위가 작고 기존 구조에 잘 얹힌다. 각도 버튼은 이미 `data-act="seta"`로 슬라이더를 움직이고(`missions.ts:233`, `main.ts:40`), 기록은 `on.land`의 `s.exp`에 이미 있으므로 상태 계산에 새 데이터가 필요 없다. 아래는 계획에서 반드시 정해야 하는 지점이다.

- R4: [권장] **FR-003("어떤 방법으로 바꿔도 곧바로")을 만족하는 갱신 경로가 지금 없다.** 튜토리얼 카드 본문은 `emit()`(게임 이벤트)과 카드 안 클릭에서만 다시 그려진다(`tutorial/index.ts:69,90,96`). 슬라이더 드래그·± 버튼·키보드 화살표는 `main.ts:53`의 `input` 리스너에서 `updateStats()`만 부르고 `tut.render`를 부르지 않는다. 그래서 ① 각도 버튼을 누르면 US2-2는 통과하지만, ② 드래그·±·키보드로 50.5°가 되면 US2-3과 FR-003이 실패한다. 테스트가 버튼 클릭만 하면 이 결함을 놓친다. 계획에는 `input` → 카드 다시 그리기를 한 줄로 명시하고, 그때 `render(false)`(스크롤 없음)를 써야 한다. `render()` 기본값은 강조 대상(`field`)으로 `scrollIntoView`를 호출해(`tutorial/index.ts:80`) 드래그 중 화면이 튄다. 또 `body.innerHTML` 교체로 카드 안 초점이 사라지므로(§Edge Case의 "초점 이동 방식") 드래그·키보드 사용 중 초점을 되돌리는 처리를 함께 정해야 한다.
  - **2차 확인.** 코드를 다시 읽어 세 경로를 구분했다: (a) 각도 버튼 클릭은 `main.ts:40` `onAction` → `setAngle` 후 `tutorial/index.ts:96`의 `render(false)`로 **갱신된다**. (b) 슬라이더 드래그·± 버튼은 `main.ts:53` `input` → `updateStats()`만. (c) 키보드 화살표도 range 입력의 `input` 이벤트라 (b)와 같은 경로다. 즉 (b)(c)만 실패한다. 15단계는 `target:()=>[FIELD()]`이고 `dim`은 `els[0].classList.add('dim')`(box-shadow)로만 그리며 `.tut-dim`은 `els.length>0`일 때 숨겨지므로(`tutorial/index.ts:74`) **슬라이더·± 버튼은 실제로 조작 가능**하다 — 즉 이 결함은 이론적이지 않고 재현된다. US2-3의 "± 버튼이나 드래그로 50.5°" 시나리오가 바로 이 경로다. 정정: R4의 "초점을 되돌리는 처리"는 과한 요구일 수 있다. 카드 안 각도 버튼을 눌렀을 때만 초점이 사라지고, 슬라이더는 카드 밖이라 `innerHTML` 교체에 영향받지 않는다. 계획에는 "슬라이더 입력 시 `render(false)`"만 넣고, 카드 버튼의 초점 유지는 §Edge Case대로 별도 판단하면 된다.
- R5: [권장] **US3-2("'쏜 각도' 버튼에 초점 → 비활성으로 읽힌다")는 그대로는 검증할 수 없다.** native `disabled` 버튼은 초점을 받지 못하고 탭 순서에서도 빠진다. 화면 낭독기 탐색 모드에서는 "사용 불가"로 읽히지만 "초점" 시나리오는 성립하지 않는다. 시나리오를 "탐색 모드에서 비활성으로 읽힌다"로 고치거나, `aria-disabled="true"` + 클릭 무시로 바꿔 초점을 유지하는 쪽을 계획에서 택해야 한다. 후자를 택하면 "완전 비활성"(§4)의 정의도 "초점은 가되 동작하지 않음"으로 함께 고쳐야 하고, 키보드 Enter/Space 무시를 테스트에 넣어야 한다. 둘 중 하나를 정하지 않으면 FR-001과 US3-2가 서로 다른 구현을 가리킨다.
  - **2차 확인.** `engine/src/tutorial/index.ts`와 `episodes/01-calculus-howitzer/src/game.ts` 어디에도 `aria-disabled`를 쓰는 곳이 없다. 기존 비활성 처리는 모두 native `disabled`다(`game.ts:42,72,99`의 `fire`, `:118,120,121`의 flight 버튼, `tutorial/index.ts:75,77`의 prev/next). 즉 저장소 관례는 native `disabled`이고, 그 관례를 따르면 US3-2의 "초점" 서술만 고치면 된다. R5의 두 선택지 중 **①(시나리오 문구 수정)** 이 변경량이 가장 작다. "완전 비활성"(§4)을 유지하려면 ①을 권한다.
- R6: [권장] **NFR-003의 Firefox·WebKit 검증 위치가 스펙에 없다.** `playwright.config.ts:13`은 CI에서 firefox·webkit을 `testMatch: /(ticks|mobile)\.spec\.ts/`로만 돌린다. 새 파일(예: `angle-buttons.spec.ts`)을 만들면 세 엔진 중 Chromium에서만 실행되어 NFR-003을 만족하지 못한다. 게다가 `mobile.spec.ts`는 390px 뷰포트(`mobile.spec.ts:4`)라 360px 요구(NFR-001)를 재지 않고, 360px 검증은 `ticks.spec.ts`에만 있다(`:29`의 `[360, 768, 1280]`). 계획에 "각도 버튼 검증을 `ticks.spec.ts`에 넣는다(또는 `testMatch` 확장)"를 명시해야 NFR-003이 달성 가능해진다. 44px 측정은 `getBoundingClientRect()`로, 360px은 `setViewportSize`로. 참고로 `mobile.spec.ts:37-44`의 '작은 터치 대상 보고'는 `test(...)` 실패 처리를 하지 않고 annotation만 남기므로 이것을 NFR-001 판정으로 쓰면 안 된다.
  - **2차 확인.** 위 세 줄은 코드와 일치한다. 다만 `ticks.spec.ts`에 넣을 때 걸리는 점을 하나 더 적는다: 그 파일은 `DONE`(튜토리얼 완료) 상태로 열어(`:25,31`) 15단계 카드를 띄우지 않는다. 15단계 버튼을 재려면 `open(page, CURRENT, {tutorial:true})` + `walkTutorial`로 15단계까지 가야 하는데, `ticks.spec.ts`는 `open`/`walkTutorial`을 이미 import하므로(`:4`) 가능하다. 다만 그 경로는 단계당 1.2초 진행(`helpers.ts:101`)이라 15단계까지 수십 초가 걸린다. `parity.spec.ts`가 `timeout: 900_000`을 쓰는 이유와 같다. 계획에 테스트 시간 예산(타임아웃 상향)을 함께 적어야 CI에서 flake가 나지 않는다.
- R7: [권장] **C-003/SC-004의 허용 범위가 실제 비교 대상보다 좁다.** `parity.spec.ts`의 튜토리얼 비교는 단계마다 `tutBody` HTML과 `sScore`·`hud`·`banner`·`log`를 통째로 비교한다(`helpers.ts:55-56`, `parity.spec.ts:40-48`). 15단계 카드 본문에는 각도 버튼의 상태(클래스·`disabled`)가 그대로 들어가므로, **15단계의 `tutBody` 스냅샷은 반드시 달라진다.** C-003은 이를 "허용"한다고 하지만 비교 코드에는 예외 처리가 없다. 또한 `snapshot()`의 `norm()`(`helpers.ts:53`)은 색 코드를 소문자로만 바꾸고 클래스명은 `fire`/`sec`만 정규화하므로, 새 상태 클래스가 HTML에 남아 diff가 난다. 계획에서 ① 15단계 스냅샷에서 각도 버튼 상태만 마스킹하거나, ② legacy 쪽에 같은 상태 표시를 넣어 비교하거나(불가능), ③ C-003을 "15단계 `tutBody`의 각도 버튼 상태만 비교 제외"로 구체화해야 한다.
  - **2차 정정 — 1차가 든 근거 하나는 틀렸다.** 1차는 "`walkTutorial`이 카드 안 `.act` 버튼을 순서대로 눌러 fired 버튼이 비활성이 되면 legacy와 발사 각도 순서가 달라진다"고 적었다. 실제 `helpers.ts:95-98`은 `#tutBody .act`를 `(c>>1) % acts.length`로 **순환**하며 누르고, 비활성 버튼은 `.click()`이 무시되므로 current 쪽은 자동으로 다음 각도로 넘어간다(`tap`은 `element.click()` 직접 호출이라 `disabled`면 아무 일도 없다). 각도 순서는 달라지지만, legacy도 같은 순환이라 4발째에 4각도가 채워지는 시점은 같다. 즉 "명중 여부가 갈려 `newTarget()`이 발산한다"는 1차의 서술은 근거가 약하다 — 15단계는 `ignore the flag`라 명중해도 게이트가 각도 집합만 보므로 진행 자체는 동일하다. **다만 결론(C-003 범위를 좁혀야 한다)은 더 강하게 유지된다**: 원인이 각도 순서가 아니라 15단계 `tutBody` 자체의 HTML 차이이기 때문이다.
- R8: [권장] **NFR-001은 크기만 재고 간격·줄바꿈을 규정하지 않는다.** 360px에서 5개가 한 줄에 들어가더라도(1절) 현재처럼 인라인 공백(약 4px)으로 붙이면 40/45/50 버튼 사이가 4px라 오터치가 난다. 이 미션은 오터치 한 번이 곧 기록(되돌릴 수 없음)이라 결과가 크다. 5×48px + 4×8px = 272px ≤ 287px이므로 8px 간격은 360px에서도 들어간다. NFR-001에 "한 줄, 버튼 사이 최소 8px(또는 flex `gap:8px`)"를 넣고, SC-003의 측정 항목에 간격을 추가하는 편이 좋다. 줄바꿈을 허용하려면 카드가 세로로 더 길어져 15단계 표가 스크롤 밖으로 밀리므로, 한 줄 고정이 학습 흐름에도 낫다.
  - **2차 보강 — 287px에서는 여유가 15px뿐이다.** 클래식 스크롤바 환경(Chromium 데스크톱, 1절)에서 내용 폭은 287px다. 44px 최소 폭 + 8px 간격이면 5·44 + 4·8 = 252px로 35px 여유가 있지만, 버튼 폭을 지금처럼 글자에 맞춰 잡으면(answers 추정 52px) 5·52 + 4·8 = **292 > 287**로 넘쳐 두 줄이 된다. 즉 R8의 "8px 간격"은 버튼 폭을 44~51px로 고정할 때만 성립한다. 계획에 `flex:1 1 0` + `justify-content:space-between`처럼 여유를 자동 분배하거나, `min-width:44px` + `padding` 축소로 폭 상한을 정하는 방식을 명시해야 한다. NFR-001의 판정도 "각 버튼 ≥44×44" + "한 줄(모든 버튼 `offsetTop`이 같음)" + "`scrollWidth ≤ clientWidth`" 세 가지로 적는 편이 안전하다.
- R9: [권장] **NFR-001에 버튼 폭 상한 또는 배치 방식을 숫자로 넣어야 한다.** R8의 간격 요구와 V1의 여유 계산을 합치면, 360px에서 한 줄을 유지할 수 있는 조건은 "버튼 폭 ≤ 51.0px (간격 8px, 내용 폭 287px)"이다. 계산: (287 − 4·8) / 5 = 51.0px. 현재 `.act`의 `padding:8px 12px` + 테두리 1px + '30°' 글자 폭(약 22~26px)이면 폭이 48~52px 범위에 걸려 **경계에 있다**. 스펙은 "44×44 이상"만 요구하고 상한을 두지 않으므로, 구현이 폰트·padding을 조금만 키우면 360px 클래식 스크롤바 환경에서 두 줄이 되어 NFR-001("가로 스크롤 없음")은 통과하지만 "한 줄"이라는 의도(R8)는 깨진다. NFR-001에 ① "한 줄"을 명시하고, ② 폭을 `flex:1 1 0`처럼 여유 분배로 정하거나 `max-width`를 함께 적어야 한다. 이 상한은 320px 화면에서는 더 빡빡해진다(오버레이 스크롤바면 내용 폭 262px → (262−32)/5 = 46.0px, 클래식 15px 스크롤바면 247px → 43.0px로 44px 미달). 헌장 PRJ-004는 360px 기준이므로 320px은 범위 밖이지만, 계획에서 `@media (max-width:359px)` 처리 여부를 한 줄 적어 두면 안전하다.
- R10: [권장] **NFR-001(44px)을 만족하려면 `.tut-body .act`를 직접 키우면 안 되고, C-002와 충돌한다.** 15단계(15/22) 각도 버튼은 다른 단계의 조작 버튼과 **같은 클래스** `.act`를 쓴다(`missions.ts:233`의 각도 버튼). 같은 클래스는 조준 미션(19/22)·실전(20/22)의 `setaBtn`(30·35·50·60° "넣기")·장약 버튼에도 쓰인다(`missions.ts:40,55,70,74`). 현재 `.act`는 `padding:8px 12px`로 높이 41.25px(2절)라 44px에 2.75px 모자란다. 구현자가 `.tut-body .act{padding:11px 12px}`처럼 전역으로 고치면 C-002("엔진의 공용 튜토리얼 버튼 모양은 바꾸지 않는다")를 어기고, 19/22·20/22 카드 레이아웃까지 바뀐다(그 단계들은 `tutBody` HTML이 parity 비교 대상이기도 하다 — R7). 따라서 15단계 버튼에만 붙는 **전용 클래스**(예: `.act.angbtn`)를 만들어 그 안에서만 `min-height:44px`, `min-width:44px`, `flex` 배치를 적용해야 한다. 스펙 §4가 "버튼 5개의 모습"만 말하고 클래스 범위를 정하지 않아, 계획에서 이 경계를 못박지 않으면 C-002 위반이 재현된다. 참고로 헌장의 승인된 44px 예외 목록(언어 버튼, ± 버튼, 슬라이더, 장약·모드 버튼)에 **튜토리얼 `.act` 버튼은 없다** — 즉 지금 이 버튼들은 예외 없이 PRJ-004 미달 상태이고, 이 미션이 15/22의 5개만 고치는 셈이다. 19/22·20/22의 `.act` 버튼은 범위 밖으로 남으므로, PRJ-005에 따라 사람에게 "나머지도 후속으로 고칠지"를 확인할 가치가 있다.
- S6: [사소함] Mermaid 상태도에 FR-004 우선순위가 드러나지 않는다. `현재 --> 쏜각도`는 있지만 "쏜각도에서 슬라이더가 그 각도로 와도 현재로 승격되지 않는다"는 전이가 없어, 그림만 보면 두 상태가 겹칠 때 규칙을 알 수 없다. `쏜각도 --> 쏜각도: 슬라이더가 이 각도가 됨 (현재로 바뀌지 않음)` 한 줄이나 아래 각주를 붙이면 표·시나리오와 그림이 맞는다.
- S7: [사소함] C-005(새 문구 양언어)는 있으나, 상태별 접근성 이름의 **예시**가 없다. "현재"는 `aria-pressed`(기존 `.mode` 패턴)로, "쏜 각도"는 `disabled`로 읽히면 별도 이름이 필요 없어 보이지만, 화면 낭독기가 "30도, 사용 불가"만 읽으면 왜 못 누르는지 알 수 없다. `aria-label="30도, 이미 쏨"` / `"30°, already fired"` 같은 예시를 스펙에 하나 두면 번역 누락(PRJ-007)과 설명 부족을 같이 막는다. 이 이름은 버튼 5개 상태에 따라 바뀌므로 카드 재렌더(R4)와 같은 경로에서 갱신해야 한다.
